## 1. Charted pins: recognise an address once, where it is defined

**Acts on:**
- (c) an objection to the M-log family: R4-R1-1 #3, R4-R1-2 #2, R4-R1-3 #3, R4-R1-4 #4, and the address half of R4-R1-5 #4;
- (a) it extends R4-R1-1 #3's `addrOf`.

**Seed:** `KIqr` … `CIqKC`. The same `Iq` is met twice. Recognise it the first time and reuse it the second time; never recognise it again.

### The objection

Every round-1 label proposal moves the `omega` from separation to recognition, but none of them prices recognition.
- `rd_log`, `rd_wr_chart` and `fwd` only fire once an address is in the form `w.at ρ + o`.
- The machine never produces that form. It produces a `BitVec 64`: for example `x25 + (ins >>> 23 &&& 0x1ff) <<< 4 + 8`, read back as `Nat` through `toNat`.
- Putting it into chart form requires `(w.base + 16·b + 8) % 2⁶⁴ = w.base + 16·b + 8`. That is an `omega` against `Ranges.base_hi`, inside `Nat.mod_eq_of_lt`.

The KIT-2 ledger's FORPREP profile names exactly this: "2–4 `omega` runs per side condition through `Nat.mod_eq_of_lt`".

So if `addrOf` (R4-R1-1 #3), `pinChart` (R4-R1-2 #2) or "fold to `at r o` by `simp only`" (R4-R1-4 #4) runs at every *read*, each read still pays one no-wrap `omega` per address. MODK seg4 reads `K[C]`'s payload through two stores: the read address, plus the two store addresses for the log's tags. That is three recognitions.

There is a second objection, to **R4-R1-5 #2's `cellOf : Nat → Cell`**, an `if` cascade on a concrete `Nat`. Evaluating it on `w.base + 16·b + 8` compares against `w`-dependent bounds, so it is `omega` again, run every time it is asked. A tag that is *computed* from the address is as expensive as the separation it replaces. The tag has to be *carried* instead.

### The idea

Chart a pin when the instruction that writes it executes, and carry the chart in the pin.

The kit's pins already come from a small set of definitions, so a pin's value is stated in chart form from the start:
- `s9 := base` at the head;
- `a5 := s9 + 16·b` (`slli` + `add`);
- `a0 := s9 + 16·a + 8`;
- `ld k,0(sp)`.

The form is:

```lean
structure CPin where reg : Reg; rgn : Rgn; off : Off      -- Off := lit n | slot (f : Field) (c : Nat)
def CPin.val (w) (x : CPin) : BitVec 64 := BitVec.ofNat 64 (x.rgn.addr w + x.off.eval ins)
```

- **No-wrap, once.** No-wrap is proved once, per region, inside the atlas: `Rgn.addr w + Rgn.size p < 2⁶⁴`. The region of R4-R1-1 #3 gains an `extent_lt` row.
- **Arithmetic on charted pins.** An `addi`/`add`-by-a-literal on a charted pin is the lemma `cpin_addi : (x.val w + n) = {x with off := x.off + n}.val w`, under `x.off + n < x.rgn.size`. The bound is a `decide` on literals, or one bounded-field fact for `slot b` (`b < 256`, from the instruction format).
- **Loads.** A load `ld rd, o(rs)` with `rs` charted gives the address `{rs with off := rs.off + o}` with no `toNat` step. Then `rd_log`/`fwd` take over.

### Core rules

**The address side of L4-split′'s cost → `CPin.addr` (once).** `(x.val w).toNat = x.rgn.addr w + x.off.eval ins`, from `extent_lt`. It is the only `Nat.mod_eq_of_lt` in the system.

**Pin transport → `cpin_addi`, `cpin_add_slot` (once each).** Every pin-defining instruction F1 arms use (`addi`, `add` with `slli 4` of a field) has a charted rule. There are 5–6 rules, keyed on opcode, not per arm.

**A seam with the log.** R4-R1-1 #3's `addrOf` becomes the identity on charted pins. It is still needed for unforeseen address forms, as a fallback.

### What it makes free

- **The recognition `omega`s.** In MODK's pre half, 5 segments × 2–3 addresses: about 10–15 `omega`s with a disjunctive context become 0. All the others are already removed by labels.
- **FORPREP.** It reads `R[A]`, `R[A+1]`, `R[A+2]` (tag and payload) and spills `sd a5,16(sp)`, so its 6 reads and 4 stores are addresses off three charted pins: `a0 = slot a`, `sp = cframe 0`, `ci`. That is 0 no-wrap `omega`s after the pins are charted.
- **R4-R1-5 #2's `cellOf` and `cellOf_spec`.** They are not needed.

### What it costs

- **Setup:** `CPin`, `extent_lt` per region (inside `Rgn.sep_sound`'s proof), and 6 transport lemmas. About 80 lines, forecast.
- **`pins_of` changes once.** The pin it emits is a `CPin` application, not a raw sum. That is the second runner mode that R4-R1-5 #1 already priced.
- **Harder: pins that are not addresses** (`ins`, loaded payloads). They stay raw. That is correct: they are never dereferenced in F1. The exception is a string payload passed to `luaV_equalobj` (a heap pointer), which gets the `strObj x` chart from `ValRepr` at the load (idea 3).

### Theories

- **Static single assignment and value numbering** (Cytron et al., TOPLAS 1991; Alpern, Wegman and Zadeck, POPL 1988) **[check]**. Known. A fact about a value is attached at its unique definition and read at every use.
- **Pointer provenance in C semantics** (Memarian et al., "Exploring C semantics and pointer provenance", POPL 2019) **[check]**. Known. A pointer carries the allocation it came from, so disjointness is a provenance comparison, not arithmetic.
- **Geocoding at ingest**, from cartography and GIS. A postal address is geocoded once when a record enters the system, and every later spatial query uses the stored coordinates. *Analogy; novel as a proof device.*

### Pilot

- **Smallest build:** `CPin`, `extent_lt` for `slot`/`kslot`/`savedpc`/`ltop`, `cpin_add_slot`, on top of the pilot of R4-R1-1 #3.
- **Cheap falsifier (before building anything):** split `ProfModk`'s 341 `omega` calls into those whose goal mentions `% 2^64` or `toNat` and those that are pure separations.
  - If the first group is under 20%, this idea is unnecessary, because labels alone carry the load.
  - If it is over 40%, labels without charting will not bring seg2 or seg4 under 10k.
- **On the held-out cases:** it serves FORPREP and IDIV (budget) and MODK (refactor), and nothing else.

## 2. Segment-local discharge: the generated segment pays its own rent

**Acts on:**
- (b) it combines R4-R1-5 #1 (`At`, a `Loc` table per arm pc) with R4-R1-3 #4 (generated cut placement);
- (c) it objects to R4-R1-5 #1's verified `locXfer` (200–300 lines) and to R4-R1-1 #4's path certificates (600–900 lines). Both build a second symbolic evaluator in Lean, when a generator that already proves every segment in its own declaration exists;
- it answers the press question "if M-log's heartbeat claim is false, what carries the budget?"

**Seed:** `R5UUUvb`. Three identical units sit side by side, and each stands alone. Each segment pays its own budget, and the arm only adds the receipts.

### The observation

The budget is per declaration, and §1b.3 measured cost as *additive in segments*. So nothing that lowers the per-load cost *inside the arm's declaration* can be the only lever. If M-log's claim fails (for example if type checking of the memory terms, not `omega`, dominates), the per-load cost stays at 15–20k, and only moving work to *another declaration* helps.

The project already has one declaration per segment: the generated `seg_<lo>_<hi>`. Today those lemmas are relation-free (`SegSt` to `SegSt`, side conditions as named hypotheses), so every separation side condition is discharged *in the arm*, by `kit_disch`, once per path that crosses the segment. MODK's seg2 is crossed by every general path of MODK, and the same goal is re-proved for each.

### The idea

Give the generator one more boundary mode, `"boundary": "at"`, alongside `"segst"`. A segment is then stated between two rows of R4-R1-5 #1's `Loc` table: `At p s w ins (locs lo) wr → ∃ c', StepsN … ∧ At … (locs hi) wr'`, under the hypothesis `Ranges p w`.
- Its load side conditions are discharged *inside the generated segment declaration*, by the same kit tactics the arms use today. The separations behind `K[C]`'s tag through `savestate`'s stores are proved there, once.
- The row `locs hi` says `a5 ↦ kTag c`, so the arm receives the *value* and not a read obligation.

R4-R1-5 #1 wanted a verified Bool evaluator `locXfer` with soundness proved once. Here each segment's transfer is proved *by the generator's own run of the kit*, so it needs no evaluator and no soundness theorem. The trust is the same as today's generated segments: the kernel checks them.

### Core rules

**The cost side of L4-split′ → `At.seq` (once).** `At lo → At mid` and `At mid → At hi` give `At lo → At hi`. Composition is by name, and the boundary is a table row.

**A call node inside the table → `At.call` (once).** This is R4-R1-5 #1's rule, with the frame computed as in idea 5.

**The close → `At.close` (once).** `At (locs head) wr c → VmRel p c s'`, given that the `slotVal` entries in `wr` match `s'`.

The arm's proof is the kernel's case split followed by a chain of `At.seq`. That chain is the path, and it is a list of names.

### What it makes free

- **The per-load cost in the arm, with or without M-log.**
  - Forecast: each segment application costs what seg3 (`j`) costs today, about 6k.
  - MODK's general path is 5 + 3 segments. 8 × 6k + close ≈ 70k: one declaration, with no `armBody_split`.
  - FORPREP's integer path is about 10 segments and 2 call nodes. 12 × 6k + close ≈ 90k: one declaration.
- **`ArmPre`, `AtRet`, `divFrame`, and FORPREP's `fp_pre`/`FpInts`/`fpFrame`/`FpMem`.** Every boundary is a row (as in R4-R1-5 #1, R4-R1-3 #4 and R4-R1-4 #5).
- **R4-R1-3 #4's cost model and cut placement.** They are unnecessary while the arm stays under 200k. If a long arm such as CALL exceeds it, a cut at any row is free, because L4-split′'s measured setup is about 5k.
- **The 557k fallback.** The arm never unifies a store chain, since it never sees one.

### What it costs

- **Setup.** `Loc`, `⟦·⟧`, `At` (R4-R1-5 #1's smallest build, about 150 lines), `At.seq` and `At.close`. The generator mode emits `At` statements and runs the kit inside each segment. It already composes post-pins in `lcall_frames.py`; this prints them in `Loc`.
- **Risk to the brief's forbidden list.** It is *not* "a generator that emits per-arm proofs". It emits per-segment proofs, exactly as `gen_segment.py` does today, with a stronger boundary. The coordinator should confirm this reading.
- **Harder: generality.** A segment must be proved generic in the instruction fields (`b`, `c` as `Field ins`), since every path through it, for every `ins`, uses one lemma. The `slot b` vs `slot c` separation then needs `b ≠ c` or an aliasing case split in the segment. Today the arm has the concrete field relation in context.
  - Fix: a segment takes the field relation as a named hypothesis from the row (`wr`'s disjointness). It is discharged once per arm path by `decide` on `Field` names.
- **The per-segment declaration still has to fit 200k.** seg4 is 42k inside the arm today, which leaves wide headroom.

### Theories

- **Separate compilation with link-time composition.** Known. Units are checked once and linked by name; the linker never re-checks a unit.
- **Proof-carrying code** (Necula, POPL 1997) **[check]**. Known. The unit carries its own proof, and the consumer only checks the interface.
- **Prefabrication in construction ("modular building").** Modules are certified at the factory, and the site does only assembly and connection inspections. *Known practice; novel as a proof-cost device.*
- **Amortised analysis, the banker's method** (Tarjan, SIAM J. Alg. Disc. Meth. 1985) **[check]**. Known. Each segment prepays its cost once, and all later uses are charged nothing.

### Pilot

- **Smallest build:** `Loc` restricted to `ptr`, `slotTag`, `slotVal`, `kTag`, `kVal`, `res`, `dead`; `At`; `At.seq`. Regenerate **only MODK's seg2 and seg4** in `"at"` mode.
- **Falsifier (cheap):** two numbers.
  - (i) The standalone heartbeats of the regenerated seg4. Prediction: under 60k.
  - (ii) The heartbeats of *using* it in a test arm path. Prediction: under 10k.
  - If (ii) is above 20k, type checking the `At` row at the boundary dominates, and the idea fails.
- **Held-out:**
  - FORPREP: one declaration per exit (up/down × run/skip).
  - IDIV: the same.
  - MODK refactor: `modk_*` with no `ArmPre`.

## 3. Footprints registered against the arena and derived from the constructor

**Acts on:**
- (c) objections to all three M-str variants:
  - R4-R1-1 #5, R4-R1-2 #1 and R4-R1-5 #2 use the contiguous `fp = [ts, ts+24+len]`;
  - R4-R1-3 #5 holes `+16` "of every object";
  - R4-R1-4 #1's `tsFoot` includes `+16..23` for all strings;
  - all five state disjointness against `Win`.
- (a) it extends R4-R1-4 #1 / R4-R1-2 #1, the cheapest variant (see the variants table at the end).

**Seed:** `RIS2MdPCvMd0MfBT`. The token `Md` stays put while a `0` fence appears beside it. The object stays; the window, the fence, moves.

### Counterexamples

Three concrete places break round 1.

1. **The `+16` word is variant-dependent** (`lobject.h:391`, `union { lnglen; hnext }`).
   - For **long** strings, `+16` is `lnglen`. `luaS_eqlngstr` reads it at `0x80017188` (`ld a4,16(a0)`) and `0x8001718c`, and `TStringRepr.long` demands it (`rd64 m (ts + tstringLnglenOff)`). R4-R1-3 #5's hole at `+16` "of every object" therefore erases the length that EQ-long needs.
   - For **short** strings, `+16` is `hnext`. It is written to *live* strings by `tablerehash` (`lstring.c:72`, from `luaS_resize`, which `growstrtab` calls during CONCAT's `internshrstr`) and by `luaS_remove` (`:170`, which writes the *predecessor's* `hnext` when GC frees a string). So R4-R1-4 #1's `tsFoot ⊇ +16..23` for all strings, and the contiguous `[ts, ts+24+len]` of R4-R1-1 #5, R4-R1-2 #1 and R4-R1-5 #2, are *false* invariants once CONCAT or GC runs. The same goes for `next` at `+0` and `marked` at `+9`.
   - For **long** strings, `extra` (`+10`) and `hash` (`+12`) are written lazily by `luaS_hashlongstr` (`lstring.c:55–56`) the first time a long string is a table key. That happens in F2's GETTABLE/SETTABLE.
2. **VARARGPREP moves `Win`.** `luaT_adjustvarargs` copies the function and its fixed parameters above the varargs and advances `ci->func`, so `w.base` changes.
   - Any footprint fact stated *relative to `Win`* (R4-R1-4 #1's index `W := Win p w`, R4-R1-1 #5's `Core.owned`, R4-R1-5 #2's `Core.bastion`) must be *re-proved for every live string against the new window*, and the only proof is "strings are not in the Lua stack at all".
   - R4-R1-3 #5 is worse. The old slots become varargs, *outside* the new `Win`, so `w'.mo` must be *re-filled* there. That breaks its key selling point, that "`w.mo` never changes".
3. **The fact everyone actually uses is not about `Win`.** It is that strings are not in any *chunk the VM writes* during F1. Those chunks are the Lua stack block, the C stack, the `CallInfo`, and `lua_State`.

### The idea

Two changes, both inside `ValRepr.str` (R4-R1-4 #1's placement, which costs no new relation field).

**(i) The footprint is derived from the constructor, not written.** Define `TStringRepr.supp : TStringRepr m ts s → Set Nat` per constructor, as exactly the addresses that constructor reads:
- `short`: `+8`, `+11`, `[+24, +24+len]`;
- `long`: `+8`, `+16..+23`, `[+24, +24+len]`.

Prove `Sealed` (R4-R1-4 #1's notion) once, by cases on the constructor. The footprint then cannot drift from the representation, and the GC, intern-table and hash-cache bytes (`+0`, `+9`, `+10`, `+12`, and `+16` of short strings) are outside it *by construction*.

**(ii) Disjointness is registered against the arena, not the window.** Add to `RelPtrs` the stack block `[w.stk, w.stkEnd)` (`L->stack` to `L->stack_last + EXTRA_STACK`). Then:
- `Arena p w := StackBlk w ∪ CStack ∪ Scratch`, with `Win ⊆ Arena` proved once from `Ranges`;
- the `str` constructor of `ValRepr` carries `∀ a ∈ supp, ¬ Arena p w a`.

VARARGPREP and every CALL that does not reallocate keep `stk`/`stkEnd`, so the conjunct is untouched when `base` moves. `luaD_reallocstack` (F2) moves the block to a *fresh* `malloc` chunk, disjoint from live string chunks by `DlHeap.HeapAt`'s chunk disjointness: one lemma at that one site.

### Core rules

**L4-str → `ValRepr.str_bytes` (once).** `Core p c s w → s.regs j = some (.str t) → TStringReprT c.σ.mem x t`, by `Sealed.along` with `Win ⊆ Arena`.

**L4-str′ along any run → `Sealed.along_arena` (once).** A run whose writes lie in `Arena` preserves every string. F1 arms and their callees `luaV_equalobj`, `luaS_eqlngstr`, `memcmp`, `l_strcmp`, `strcmp`, `strlen` and `luaV_tointeger` write only `Scratch` and `CStack`. `kit_frame` or the region log (idea 1) decides this.

**Preservation → free.** MOVE, LOADK, GETUPVAL and the arms' def ports copy a `ValRepr` *together with its proof*, so no `owned_step` (R4-R1-1 #5) or bastion-preservation obligation (R4-R1-5 #2) exists.

### What it makes free

- **The four premises** (with idea 4's scans), on both short and long strings. The short-string path of LT still compares contents through `l_strcmp`, so it needs `+11` and not `+16`.
- **VARARGPREP's footprint obligation:** 0 lines, instead of a re-proof against `Win'`.
- **CONCAT's and GC's header writes:** outside `supp` by construction. CALL print needs no "header writes avoid footprints" lemma.
- **A future table representation.** Its `supp` is again derived from *its* constructor, and the array part is excluded from stability because it is mutable. See the caveat below.

### What it costs

- **Setup:** `TStringReprT` (the total-read shadow, as R4-R1-4 #1 noted, since `BytesAt` is presence), `supp`, `Sealed` by cases, two `RelPtrs` fields, `Win ⊆ Arena`, and the boot-witness check `supp ∩ Arena = ∅`. About 90 lines plus the witness change.
- **A caveat against generalising (c, to R4-R1-4 #1's "later heap objects use the same `Sealed`").** Tables in F2 are *mutable* by the arms themselves (SETTABLE writes the array part). `Sealed` gives frame preservation, which is right for immutable strings and wrong for tables, whose representation must be *updated* along the run. Do not sell this as the table abstraction.
- **Alignment is still missing.** `memcmp` takes its word loop only if `(a0|a1)&7 = 0` (`0x800361a0–0x800361a8`). With `a0 = ts+24`, that needs `ts ≡ 0 mod 8`, an allocator fact. Put it in the same conjunct (`ts % 16 = 0` from `malloc`), or prove both loop paths. Idea 4 makes the second option cheap.

### Theories

- **Ownership types** (Clarke, Potter and Noble, OOPSLA 1998) **[check]**. Known. An object's footprint is owned by a context and disjoint from other owners' writable state.
- **Precise assertions** (O'Hearn, Yang and Reynolds, "Separation and information hiding", POPL 2004) **[check]**. Known. A predicate with a unique footprint, which is what `supp` per constructor makes `TStringRepr`.
- **Torrens title registration**, from land law (South Australia, 1858) **[check]**. Known as a field. A parcel's title is registered against the *register*, not against whoever currently occupies the neighbouring land, so the title survives every change of neighbour. Here the string is registered against the arena, not the moving window. *The analogy is novel.*
- **Arena allocation** (Hanson, "Fast allocation and deallocation of memory based on object lifetimes", SP&E 1990) **[check]**. Known.

### Pilot

- **Smallest build:** `supp` and `Sealed` for `TStringRepr`, the arena fields, `ValRepr.str`'s conjunct, and `Core.str_bytes`. Then rebuild `eq_short` and `sim_MOVE` unchanged; that is the cost to measure.
- **Cheap falsifier of the objection:** run the existing L4-str′ trace checker (§2b) on a program that triggers `luaS_resize` (many distinct short strings via CONCAT), and count writes to `+16` of *live* short strings.
  - A non-zero count kills every contiguous-footprint variant.
  - Zero means my objection is moot for the traces we have, though not in principle.
- **Held-out:** EQ-long and LT-str, with idea 4.

## 4. Loops as tail-recursive functions over the raw registers

**Acts on:**
- (b) it combines a new machine-side rule with the pure-side libraries of R4-R1-1 #1 (`foldUntil`, `accel_sound`), R4-R1-2 #1 (`firstEvent`, lane lemmas) and R4-R1-3 #2 (`tile`);
- (c) it objects to every *affine-pin* loop rule: R4-R1-1 #1's `pins : α → Pins`, R4-R1-4 #2's `pins i`, R4-R1-5 #3's `CursorShape`, R4-R1-3 #2's `ScanAt` "tape pointer = base + k";
- (c) it objects to R4-R1-2 #4's orbit rule, which needs R4-R1-2 #3's residual transformers first.

**Seed:** the palindromes `3s3` and `a6a`, things that come back to themselves, and the runs `ZZ`, `RR`, `UUU`. A loop is a function that tail-calls itself.

### The objections

1. **Affine pins re-pay KIT's obstruction 3 on every iteration.** R4-R1-1 #1 admits this: a symbolic `p + 8·k` pin must go through `pin_eq … (by kit_val)` in the body run.
2. **The affine form is false at `memcmp`'s relay.** The word loop keeps `a2 = n − 8k` as a *count* (`addi a2,a2,-8`, `0x800361e8`). The byte loop is entered at `0x800361ac` by `addi a2,-1; addi a2,1; add a2,a0,a2`, which turns `a2` into an *end pointer*. The byte loop then compares `a0` against it (`beq a2,a0`, `0x800361bc`).
   - One counter `i` with affine pins (R4-R1-5 #3) cannot describe both loops. `cursor_chain` must re-index *and* change the meaning of `a2`.
   - `strlen`'s alignment prelude does the same (R4-R1-3 #1 admits "one more field").
   - Each such quirk is a new shape parameter.
3. **The orbit rule (R4-R1-2 #4) depends on the most expensive candidate.** It needs a function `post : Env → Env` per segment (R4-R1-2 #3) before any loop is proved.

### The idea

Use Myreen's decompilation rule. The loop state *is* the tuple of live registers and memory, as raw variables: `x : LoopSt := (a0, a1, a2, m)`. The body is one `kit_run` over the generated body segments from `SegSt h (pinsOf x) (P x.m)`. It ends in one of two states:
- `SegSt h (pinsOf (F x)) (P (F x).m)`, under guard `G x`;
- the exit `Exit (D x)`, under `¬G x`.

Here `F`, `G` and `D` are *not written*. They are the post-pins that the kit's run computes, and they are solved by unification, exactly as `kit_run` fills `_` today. The rule is:

```lean
/-- the loop's pure meaning: a big-step relation, total where it terminates -/
inductive TailRec (F : X → X) (G : X → Bool) (D : X → Y) : X → Y → Prop
  | stop : G x = false → TailRec F G D x (D x)
  | step : G x = true → TailRec F G D (F x) y → TailRec F G D x y

theorem tailrec_run
    (body : ∀ x, Triple (SegSt h (pinsOf x) (P x.m))
                        (fun c => (G x ∧ SegSt h (pinsOf (F x)) (P (F x).m) c) ∨ (¬G x ∧ Exit (D x) c)))
    (term : TailRec F G D x₀ y) :
    Triple (SegSt h (pinsOf x₀) (P x₀.m)) (Exit y)
```

The proof is by induction on `TailRec`, once.
- **Termination** lives entirely on the pure side, as a fact about `F` and `G`. It is never a machine measure.
- **Loop to loop** is plain `Triple.seq`, and the relay at `0x800361ac` is just the second loop's entry. No re-indexing is needed: `a2`'s change of meaning is whatever the entry segment computes.
- **Rotated loops** take `h` as the DFS head (`0x800361c0`).
- **Multiple exits** use `D x : Y` with a sum type.
- **Calls in the body** are call nodes (idea 5).

Each loop's *specification* is then a lemma about the pure `TailRec F G D`, stated against a class lemma from round 1:
- **nil fill.** `F (a5, a4, m) = (a5+16, a4, m[a5+8] := 0)`, guard `a5+16 ≠ a4` (from `0x8001d2a8–0x8001d2b0`: `addi a5,a5,16; sb zero,-8(a5); bne a5,a4`). `TailRec … = tile` comes from R4-R1-3 #2's `tile` with the cell `[(−8, const 0, 1)]`, as one *pure* lemma per class, valid for all 5 fills.
- **`memcmp`.** Word and byte `TailRec`s are related to `firstEvent` (R4-R1-2 #1) through `ld_eq_iff` and the relay lemma `foldUntil_append` (R4-R1-1 #1).
- **`__muldi3`, `__udivdi3`.** The pure functions are the shift-add and shift-subtract recurrences, and the copied `Muldi3Spec`/`DivLoops` lemmas are already about them.

### Core rules

**L4-loop → `tailrec_run` (once).** There is no invariant, no measure, and no family of states. The "family" is the identity on the raw state.

**Loop specifications → class lemmas on pure functions:**
- `tailrec_tile` (store loops);
- `tailrec_firstEvent` (read scans, with the lane lemmas);
- `tailrec_shift` (soft-int).

Each is proved once per *class*, by induction on `TailRec`, a pure relation with no machine in sight.

### What it makes free

- **`loadnil_loop`, `muldi3_loop`, `udiv_norm`, `udiv_div`.** Each becomes a body `kit_run` (straight-line, no symbolic pins) plus one class lemma.
- **The 5 nil fills and 2 slot copies.** Their `F` differs (store before or after the bump, offset `−8` or `0`), but every one reduces to `tile` by the same lemma.
- **The string helpers.** `memcmp`'s two loops, `strlen`'s two and `strcmp`'s two, with no cursor-shape data and no `TapeRegs` fields.
- **CALL print's 93 back edges.** `tailrec_run` applies to every one of them, whatever its shape. Only the *pure* specifications remain, and those are ordinary functional-programming proofs, where Lean is cheapest. The class lemmas of round 1 cover only the affine and scan classes, so on the print chain they would leave most loops on the general rule with a hand invariant. This rule leaves them with a hand *pure lemma* instead, which costs no heartbeats on machine terms.

### What it costs

- **Setup:** `TailRec`, `tailrec_run`, and a `LoopSt` record with `pinsOf`. About 60 lines, forecast. The class lemmas reuse round 1's: `tile` about 70, `firstEvent` plus lanes about 110.
- **Harder: "`F` solved by unification" assumes the body run leaves post-pins as terms in `x`.** If `kit_run` normalises them with `simp` (for example `a5 + 16` into `BitVec.ofNat …`), `F` becomes whatever that normal form is. The class lemmas must be stated against the same normal form. That is one adapter per class, not per loop.
- **Harder: per-loop termination is still a fact about each loop.** For the nil fill it is `(a4 − a5) % 16 = 0 ∧ a5 < a4`, which LOADNIL's `field_b_shl` already gives. It is a pure precondition, not an induction, so it is not on the forbidden list.

### Theories

- **Decompilation into logic** (Myreen, Gordon and Slind, "Machine-code verification for multiple architectures", FMCAD 2008; Myreen's thesis, Cambridge 2009) **[check]**. Known. Machine loops become tail-recursive HOL functions, and the loop rule has no invariant.
- **"Lambda: the ultimate GOTO"** (Steele, MIT AI Memo 443, 1977) **[check]**. Known. A loop *is* a tail call, so loops and calls share one mechanism.
- **The Poincaré first-return map**, from dynamical systems. Known mathematics. A flow is studied through the map on a section transversal to it: the loop head is the section, and `F` is the return map.
- **Novel here:** the return map is solved by unification from the kit's own body run, so even `F` is never written.

### Pilot

- **Smallest build:** `TailRec` and `tailrec_run`, then `loadnil_loop` as `tailrec_run (by kit_run) term ▸ tailrec_tile`. The target is ≤ 5 lines against 25, and RETURN0's fill at `0x8001c2f4` with zero new lemmas.
- **Falsifier:** prove `memcmp`'s byte loop alone. If the body `kit_run` from raw `x` costs more than the affine version (measured in heartbeats), or the unifier fails to solve `F`, then the affine rules win.
- **Held-out:** EQ-long (`memcmp`) and LT-str (`strlen`, `strcmp`, and `l_strcmp`'s chunk loop, whose body has three call nodes). There is no effect on FORPREP or IDIV.

## 5. Derived clobber sets, with the link register as data

**Acts on:**
- (c) it objects to R4-R1-1 #2 (`∀ρ` over `calleeSaved ∪ {sp, gp, tp}`, "the ABI's" frame);
- (b) it identifies R4-R1-1 #2, R4-R1-4 #5 (`call_poly` with `clob`) and R4-R1-5 #5 (`call_frame_free` with `Fp f`) as one rule, and picks the cheapest instance.

**Seed:** `EMEE`, a regular run with one interloper. The calling convention is regular except where the soft-int library deviates.

### The counterexample

The integer division helpers that IDIV, IDIVK, MOD, MODK and FORPREP reach do not follow the ABI:
- **`__moddi3` (`0x8002f7b0`)** saves its return address in **`t0`** (`mv t0,ra`). It calls `__hidden___udivdi3` with `jal` (`0x8002f7bc`, `0x8002f7d4`) and returns with `jr t0` (`0x8002f7c4`, `0x8002f7dc`). `t0` is *caller-saved* in the ABI, so a `∀ρ` over callee-saved registers drops the only copy of the return address across the inner call.
- **`__hidden___udivdi3`** returns the *remainder in `a1`*, and the caller reads it (`mv a0,a1`, `0x8002f7c0`). That is a non-ABI result.
- **`__divdi3` (`0x8002f72c`)** has no body of its own. It branches into `__umoddi3`'s tail (`bltz a0,0x8002f78c`), and from there it either tail-jumps (`j __hidden___udivdi3`, `0x8002f798`) or makes a `t0`-linked call (`0x8002f7a4`). So the "callee" is a set of shared fragments with three return conventions.

The KIT ledger's "`t0` pinned by `SegSt.pin5`" is this fact, met by hand.

### The idea

The frame of a call is `pins.filter (· ∉ W f)`, where `W f` is the callee's **write set, computed by `decide` on its generated write chain**. This is R4-R1-1 #2's own `of_wrChain` bridge, but applied to the *derived* set, never to the ABI's. `call_poly` (R4-R1-4 #5) is the rule.
- `t0` is outside `W __hidden___udivdi3` (which writes `a0`–`a3` and `ra`), so it rides through the inner call with no statement.
- The return goes through whatever register the caller's code jumps on. The summary's exit is "`pc = ⟦link⟧`", with `link : Reg` a *parameter*, `ra` or `t0`.
- Results are `W f ∩ live(ret)`, the registers the return site reads. So `a1` as a result appears automatically at `__moddi3`'s return site.

### Core rules

**L4-call → `call_poly` (once; R4-R1-4 #5).** It is parametric in `link : Reg` and in `W : List Reg` with `hW : wrChain f ⊆ W := by decide`.

**Composition → `W` of a nested call (once).**
- For `jal g` inside `f`: `W f ⊇ W g ∪ local f`, by `decide` on the composed chains.
- For a tail jump (`j g`): `f` *returns through `g`'s return*. This is `FnSummary.tailJump` from the copied layer, which CLAUDE.md already lists as a fold combinator.

The frame of IDIV's two calls is then two `List.filter`s, and nothing is stated.

### What it makes free

- **`divFrame` and its "MOD-shaped" doc problem** (ROUND-4 §1b.4).
- **IDIV's `s3`/`s4` operand temporaries.** They are not in `W __divdi3`, so they ride through.
- **The six dead pins** (`s10` at MUL, MULK and IDIV; `s6`/`s10` at FORPREP) ride through too, harmlessly.
- **`SegSt.pin5` for `t0`:** not needed.
- **FORPREP's `luaV_tointeger` out-parameter.** The *memory* part of `W` is `sp+40`. That is R4-R1-5 #5's argument-relative footprint `Fp f (cellsOf args)` and it is needed, but only for memory; registers need no parameterisation.

### What it costs

- **Setup:** `call_poly` with `link` and `W`, about 60 lines. Each existing summary is restated to quantify over the frame, a few lines each: `muldi3_sum`, `udivdi3_sum`, `moddi3_sum`, `equalobj_sum`, `toint_sum`.
- **The `decide` on a write chain must reduce.** This is R4-R1-1 #2's **[check]**, still open. If the generated helper segments' chains are not first-order, `W` is emitted as data by the generator and *checked* per segment by `decide` (R4-R1-5 #5), which is equally cheap.
- **Harder: `__divdi3`'s fragments.** They are shared with `__umoddi3`, so their summaries are *per entry*, not per symbol. The generator's `gen_fn.py --entry <pc>` already takes an entry pc.

### Theories

- **Stack-based typed assembly language** (Morrisett, Crary, Glew and Walker, "Stack-based typed assembly language", JFP 2002) **[check]**. Known. A return address is a code pointer with a type that can live in *any* register, so `t0` is just where this continuation happens to be.
- **Interprocedural MOD analysis** (Banning, POPL 1979; Cooper and Kennedy, PLDI 1988) **[check]**. Known. Write sets compose along the call graph.
- **Chain of custody**, from forensics and logistics. Known practice. What matters is who holds the item at each hand-over, not which custodian a regulation names. The return address's custodian is `t0` here and `ra` elsewhere, and the record is read off the transfers, never assumed. *The analogy is novel.*

### Pilot

- **Smallest build:** `call_poly` with `link`, and `moddi3_sum` re-derived with `W __hidden___udivdi3` by `decide`.
- **Refactor:** `modk_call`'s 4 frame lines go to 0.
- **Held-out IDIV:** `__divdi3` through its `__umoddi3` fragment (the tail jump and the `t0`-linked call), then `__moddi3` on the sign-mismatch path.
- **Falsifier:** if `decide` on `__hidden___udivdi3`'s write chain exceeds about 20k heartbeats, emit `W` as checked data instead.

### If M-log's heartbeat claim is false

Cost is additive per declaration (§1b.3), so if the per-load cost inside the arm stays at 15–20k, the only lever is to **move work to other declarations**. Two candidates:
1. **Segment-local discharge (idea 2).** Each load's separation is proved in its generated segment's own declaration, once for all paths. This is the finer and cheaper of the two, because seg2 is shared by every MODK path.
2. **Generated cuts (M-cut).** Splitting costs 5k per cut (L4-split′, measured), and the statement cost is zero once boundary states are rows or terms. This always works, and is the backstop.

Charted pins (idea 1) are the third lever *if* the cost is no-wrap recognition rather than separation. The `ProfModk` classification falsifier says which.

### Cheap falsifiers of the leading combination

None of these needs a new abstraction built.

1. **Classify the 341 `omega`s in `ProfModk`** by goal shape: `% 2^64`/`toNat` vs separation.
   - If no-wrap dominates, labels alone fail and idea 1 is required.
   - If separation dominates, idea 1 is optional.
2. **Hand-write seg4 in `At` form** as a standalone declaration and use it once. If its use costs ≥ 20k, idea 2 fails, and M-cut with M-log is the route.
3. **Count `+16` writes to live short strings** on a CONCAT-heavy trace. A non-zero count kills every contiguous-footprint variant (R4-R1-1 #5, R4-R1-2 #1, R4-R1-5 #2) and R4-R1-4 #1's `tsFoot`.
4. **`decide` on `__hidden___udivdi3`'s write chain**: does it reduce, and in how many heartbeats? A failure makes `W` checked data instead of computed. That is the same rule at a slightly higher cost.
5. **Unification of `F` in `tailrec_run` on `memcmp`'s byte loop.** If the kit's post-pins are not in a form the unifier solves, idea 4 falls back to round 1's `cloop_fold`.
