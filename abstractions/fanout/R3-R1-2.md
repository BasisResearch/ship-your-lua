## 1. The constant-complement lens (`VmLens`)

### Idea

Stop writing `VmRel` as a conjunction of fields, one per resource. Write it
as a **lens**: a decoder `get : MState → Option (State × Cpl)` that splits
the head machine state into its *view* (the bytecode state, exactly the
L-C4 decoder: pc from `s11`, `R[j]` from `s9 + 16j`, out from the console)
and its *complement* `Cpl` (everything else, as an opaque, total-read
quotient of the machine). `VmRel p c s` becomes `∃ κ, get c = some (s, κ) ∧
Inv κ`.

The key move is the **constant-complement** discipline from database view
update: an arm is a correct view update iff it changes the view by `kstep`
and leaves the complement *equal* (not "related", equal as a quotient),
except for a **declared complement delta** drawn from a small fixed algebra:

```
Δ ::= id                              -- inline arms: complement constant
    | scratch(sp-frames)              -- own C frame, callee frames below sp
    | protect                         -- {ci->savedpc, L->top} := f(pc, ci->top)
    | runtime(Φ)                      -- L-C3' runtime: named footprint Φ,
                                      --   func may move (a relocation ρ)
    | Δ ; Δ
```

`Inv` is required to be **stable** under each generator of Δ, once. A new
resource (constants, `RegsOk`, savedpc, heap, console) is then *not a new
field of the relation*: it is either in the view (console, R[j]) or in the
complement (everything else) automatically, by the definition of `get`. The
only thing a resource can add is a stability obligation for the Δ-generators
that touch it, and there are four generators, not one per resource.

`savedpc`/`L->top` stop being a widening problem: they are in the complement
(the lens hides them), and `protect` is a Δ-generator whose stability is one
lemma (`Inv` does not mention `savedpc`; `L->top` is mentioned only as "≤
stack_last", which `ci->top` satisfies). The `func` move of VARARGPREP and
the reallocating CALL is a complement delta `runtime(Φ)` *with a relocation
ρ on the view's addressing*, which is the known "view defined relative to a
complement-held pointer" case: `get` reads `func` from the complement and
decodes `R[j]` at `func + 16 + 16j`, so moving `func` and moving the slots
together is a complement-only change whose view is unchanged (which is
exactly why L-C4 held across the f1_src realloc).

### Core rules

- **L-C4 → `lens_step`** (one rule): if `get c = some (s, κ)`, the arm runs
  `c ⟶⁺ c'`, `get c' = some (s', κ')`, `kstep s = some s'` and `κ' ∈ Δ(κ)`
  for the arm's declared Δ, then `VmRel p c' s'`. Proved once from `Inv`
  stability. Every per-arm "close" lemma is replaced by computing `get c'`.
- **L-C6′ → `put_get` / `get_put` on the view:** writing the def slots with
  `ValRepr` of `vals` and killing the kill slots is a *put* on the view; the
  lens law `get (put v c) = (v, κ)` is proved once for the slot layout
  (two-sided: tag byte and payload in either order, because `put` is on
  bytes and the law is about the decoded pair).
- **L-C3′ runtime → the `runtime(Φ)` generator**: stability of `Inv` under
  "any change within Φ, plus a relocation of `func` that moves `R[<A]`
  bytewise". One lemma, for all runtime callees; the callee itself is then
  only obliged to stay within Φ (a footprint check, not a value contract)
  plus deliver its view effect (the printed line, the nil results).
- **L-C3′ noreturn**: not a lens rule; it is the absence of `get c'` at any
  later head, discharged by idea 4's exit rule.

### What it makes free

- Cluster (c): every `Core.write`/`jump`/`update`/`forloop` close and every
  `*_of` transport collapses into `lens_step` + computing `get c'`
  (`text_of`, `frame_of`, `kptr_of` are the single statement "the complement
  is constant off Δ").
- Cluster (d1): relation widening. The four pending resources (savedpc/top,
  `func` moving, heap/strings/G, console growth by a callee) become three
  Δ-generators (`protect`, `runtime(Φ)` with ρ, and the view's own `out`)
  whose stability is proved once each. No further `VmRel` field.
- Cluster (c1) `RegsOk`: in the complement's `Inv`, stable under all Δ.

### What it costs

- **Setup:** defining `get` as a total function on `MState` (total reads
  everywhere, `getD 0`, which the round-2 decision already moved toward) and
  a quotient `Cpl := MState / ≈_view` where `≈_view` identifies states that
  differ only in view bytes. In Lean: `Cpl` as `MState` with the view bytes
  zeroed ("masked"), and complement equality as equality of masked states.
  Estimate 250–350 hand lines, mostly `get`'s definition and `put_get`.
- **Harder:** `get` decodes *strings* through the heap (`TStringRepr`), so a
  string register's view depends on complement bytes. The lens is then not
  "very well-behaved" (the view is not independent of the complement). Fix:
  a string's view stores the TString *pointer* plus the heap's interning
  map, and the decoded bytes are a derived function; exactly the EQ
  observation above. Budget one extra stability lemma: `runtime(Φ)` may
  *grow* the string table but not rewrite existing entries.
- `Inv` must be the right strength: too weak and `lens_step` cannot close,
  too strong and the Δ-stability lemmas fail. The current `Complement` /
  `Ranges` structures are the starting `Inv`.

### Theories

- **Known:** Bancilhon & Spyratos, "Update semantics of relational views",
  ACM TODS 6(4), 1981 (constant-complement view update). [from memory]
- **Known:** Foster, Greenwald, Moore, Pierce, Schmitt, "Combinators for
  bidirectional tree transformations: a linguistic approach to the view
  update problem", ACM TOPLAS 29(3), 2007 (lens laws GetPut/PutGet). [from
  memory]
- **Known, distant (physics):** gauge fixing: the complement's relocation ρ
  (moving `func` and the slots together) is a gauge transformation, the view
  is the gauge-invariant observable, and `get` relative to `func` is the
  choice of gauge. Used here only as the shape of "decode relative to a
  frame that the complement holds". [textbook, no specific citation]
- **Novel (as far as I know):** the Δ-algebra of *declared* complement
  deltas with a relocation generator, so that constant-complement is
  weakened exactly by the L-C3′ runtime footprint and nothing else.

### Pilot

Smallest thing to build: `get`, `Cpl`, `lens_step`, `put_get` for one
payload+tag slot store in both orders, and the `protect` generator.

- **MUL:** Δ = `scratch` (callee frame below sp; `__muldi3` is a leaf and
  writes nothing, per L-C6′). View effect: `R[A] := mul`. Needs idea 4's
  pure-call rule for the `a0` value; the lens does the close.
- **MOD:** Δ = `protect ; scratch`. Both the integer edge and the fall-through
  (pc+1, `mv s11,s3`) carry `protect`, since the stores come before the tag
  test. This is the arm that justifies `protect` as a generator; without it
  MOD needs a new `VmRel` field.
- **EQ:** Δ = `protect ; scratch`, no view write (docondjump has no defs).
  The trap reload `lw t6,40(s7)` reads the complement (`trap_word = 0`),
  which is unchanged by `protect ; scratch`: one line.
- **Refactor `sim_ADD`:** delete the ADD close; call `lens_step` with Δ =
  `id` on both edges (pc+2 with `R[A]`, pc+1 with nothing).

Bake-off metric: MOD's hand lines with no new `VmRel` field, vs. the
incumbent's forecast (new tree 56 + widening 100–250).

### Seed

`AXRYRIA` / `8i8` / `0y0` (palindromes: a thing and its round trip,
`get ∘ put`), and `DL3D` (the same letter `D` framing the middle, the
complement framing the view). The "relative to the frame" relocation came
from the `Dl` repeats at different offsets (the same content at a moved
address).

## 2. Fiber-invariant guards (`FactorGuard`)

### Idea

Every guard lemma pair in cluster (a4) says the same thing: *a machine test
on the bytes of a slot (a tag compare, `slt` on the payload, `n+1 ≤u 1`)
decides a predicate of the represented value*. Make that one theorem about
**functions that factor through the representation**.

`ValRepr mo : Tag → Payload → Value → Prop` has fibers: `nil` has 16 tags
(`t % 16 = 0`, any payload), `int i` has exactly `(3, i)`, `str s` has two
tags and any pointer to a TString of `s`. A machine test `φ : Tag × Payload →
Bool` *factors through ValRepr on a value class C* if it is constant on each
fiber over C. Then:

```
factor_guard : Factors φ C → ValRepr mo t x v → v ∈ C →
               φ (t, x) = φ (canon v)
```

where `canon : Value → Tag × Payload` picks one representative per value
(`canon (.int i) = (3, i)`, `canon .nil = (0, 0)`, `canon (.bool b) = (1|17,
0)`, `canon (.str s) = (68, ptr?)` — for strings the payload is not
canonical, see costs). `φ (canon v)` then *computes* by `decide`/`simp` to a
kernel predicate: for `φ = (t == 3)`, `φ (canon v) = v.isInt`; for `φ =
(slt x y)` on two integers, `= x.toInt < y.toInt`.

The side condition `Factors φ C` is decided **once per test shape**, over
the finite tag byte, by `decide` (256 tags × the per-tag payload law). There
are few test shapes in the whole binary: `beq/bne tag, s2` (= 3), `beq/bne
tag, 19` (float), `beq tagA, tagB`, `andi tag,15` (nil test), `slt/sltu` on
two payloads, `bgeu 1, n+1` (the {0,−1} test), `seqz`, `bnez` on `a0` after
a pure call. The pruning (L-C2′'s "F1-pruned tree") is the *same* theorem
read backwards: a branch whose `φ (canon v)` is false on every value of the
kernel's read ports at that point is dead, with no separate float-path
lemma.

### Core rules

- **L-C4 at branch granularity (the census row for a1/a4/a5) → `factor_guard`**:
  one proved rule replaces every `guard_*_t/_f` pair.
- **L-C2′ → `canon`-evaluation of the tree**: the arm's pruned tree is the
  machine tree with every guard replaced by `φ ∘ canon`, which is a Lean
  function of kernel values. Two arms share a tree iff these functions
  agree; the table row is the ALU op and constants, as L-C2′ says.
- **Kernel inversion (a5) → `decide?` on `canon`**: once guards are
  evaluated as functions of values, the arm's leaf is indexed by the same
  value case split as the kernel's body (`match Opnd.fill os vs with
  [.int x, .int y] => …`), so "which kernel edge" is `rfl` from the
  `canon`-evaluated path, and no `step_opArith`/`step_condjump` inversion
  is written per combinator: one generic `decide?_eq_some` suffices (it
  already exists in `Kernel.lean`).

### What it makes free

- (a4) guards: 40 declarations, 191 lines, and "+1 pair per new branch
  shape" become ~8 `Factors` instances (one per test shape above), each a
  `decide`.
- (a5) inversions: 19 declarations, rising 8.5 → 18.5, become the one
  generic `decide?_eq_some` plus `rfl`.
- The "missing `Supported` premise" class (BANDK's untested `K[C]`): a
  branch-free arm reads `K[C]` as a payload with no tag test, so
  `factor_guard` does not apply; the proof needs `K[C] ∈ C_int`, which
  shows up as exactly the `Supported` premise. The theory predicts the
  premise instead of it being found by a failed build.

### What it costs

- **Setup:** `canon`, `Factors`, `factor_guard`, and the 8 `Factors`
  instances. Estimate 120–180 lines.
- **Harder:** strings. `str s` has non-canonical payloads (pointers), so
  tests on string payloads (EQ's `eqshrstr` pointer compare, LT's
  `l_strcmp`) do *not* factor through ValRepr alone. They factor through
  ValRepr **plus the interning invariant** (short strings: pointer equality
  ↔ byte equality). So `Factors` must be relative to a complement invariant
  `I`: `Factors_I φ C`. In F1 this only matters for EQ/EQK on strings
  (LOADK can put a string constant in a register). This is the same
  observation as idea 1's cost; one lemma about the string table covers it.
- Tests on *two* slots (`beq tagA, tagB` in MUL/MOD's float-mixing paths)
  need `Factors` on pairs; cheap, but it is a second instance family.

### Theories

- **Known, distant (statistics):** the Fisher–Neyman factorization theorem:
  a statistic is sufficient iff the likelihood factors through it. Here a
  machine test "is sufficient" for the kernel's predicate iff it factors
  through `ValRepr`. [from memory: Fisher 1922; Neyman 1935]
- **Known (abstract interpretation):** Giacobazzi, Ranzato, Scozzari,
  "Making abstract interpretations complete", JACM 47(2), 2000:
  completeness = the concrete operation commutes with the abstraction; the
  guard is a complete test for the abstraction `ValRepr`. [from memory]
- **Known (type theory):** quotient types and "respects the relation"
  lifting (`Quot.lift` in Lean's core): `factor_guard` is `Quot.lift` for
  the fiber relation, specialised to Booleans.
- **Novel:** using the *same* factorization to derive both guard lemmas and
  the pruning of dead (float) paths, and reading missing `Supported`
  premises off factorization failures.

### Pilot

Smallest thing: `canon`, `Factors`, `factor_guard`, and three instances:
`tag == 3`, `tag == 19`, and `(n+1) ≤u 1`.

- **MUL:** tests `tagB == 3`, `tagC == 3` (and `== 19` on the pruned
  side). With `factor_guard`, the pruned tree is two `canon` evaluations and
  the leaf is `[.int x, .int y]`: zero hand guard lines.
- **MOD:** the new shape is `bgeu 1, n+1` (the `n ∈ {0,−1}` split), which is
  a pure payload test on the int fiber; one `Factors` instance
  (`decide`-free, `omega` on BitVec). The `n = 0` side maps to the kernel's
  `none` (`imod` by zero: stuck), which is what `noreturn` (idea 4) must
  discharge; the `n = −1` side maps to `imod m (−1) = 0`, a value lemma.
- **EQ:** the test is `bne k, a0` after the call. `a0` is not a slot byte,
  it is the pure call's result, so the guard is `factor_guard` applied to
  the *call's* value (`a0 = [x = y]` from idea 4), a one-line instance.
  Strings need `Factors_I` with the interning invariant.
- **Refactor `sim_ADD`:** delete ADD's guard pairs; `factor_guard` on
  `tag == 3` twice.

### Seed

The case pairs `Uu` and `Dl`/`DL`/`lD`: one letter, several spellings,
i.e. one value, several (tag, payload) representatives. The fiber of `nil`
(16 tags) is `Uu` squared. `496` (perfect: equal to the sum of its parts)
suggested "a test is determined by its parts on each fiber".

## 3. The commuting write-log commit (`StoreLog`)

### Idea

L-C6′ says: an arm's stores land in its edge's ports, its own C frame,
`{savedpc, L->top}`, and callee frames below `sp`; four byte-level shapes
cover every non-CALL store, in compiler order. The incumbent pays for each
*shape × order* (`slotStore_sb`, `_sd_sb`, `_copy`, `_copy_tv`,
`ForStore`). Replace the ordered store sequence by its **write log**: a
finite map `Addr ⇀ Byte` of last writes, obtained from the store sequence
by one generic fold. Disjoint writes commute, so the log is order-free; a
tag-then-payload store and a payload-then-tag store produce the *same* log.

Then one **commit rule**:

```
commit : Core p c s w →
         mem c' = mem c ⊕ log →
         dom log ⊆ Slots(e.defs ∪ kills e) ∪ Frame(sp) ∪ Protect ∪ Below(sp) →
         (∀ j ∈ e.defs, ValRepr w.mo (log.tag j) (log.val j) (vals j)) →
         Pins c' w e.tgt → RegsOk c' → out c' = out c ++ print →
         Core p c' (s.apply line e o) w
```

`log.tag j` / `log.val j` read the log (falling back to `mem c` for bytes
not written: the "tag-only" LOADTRUE shape writes 1 byte and leaves the
payload, which `ValRepr .bool` ignores; FORLOOP's payload-only stores leave
the tag, which is already `3`).

The commit rule quantifies over *all* edges of *all* kernels: `e.defs`,
`kills e`, `vals` come from `decide?`, so there is one rule for `setR`,
`opArith`, `forloop`, `setNils`, `callK`, `concatK`, `testsetK`.

### Core rules

- **L-C6′ → `commit`** (one rule). The four store shapes are four ways of
  building a log; the rule does not see the shapes.
- **L-C4 at the head → `commit` + `Pins`**: the value half of L-C4 is the
  `ValRepr` premise per def port; the frame half is the domain premise.
- **Kill ports (`Cert`/`HStep` in `Kernel.lean`) → the domain premise**:
  a kill port's slots may be in `dom log` with *any* bytes, which is
  exactly `HStep`'s "every kill port holds an arbitrary value". So the
  existing `certain_answers` theorem connects directly: the machine run is
  an `HStep` run, no CALL special case.

### What it makes free

- Cluster (c): all per-shape store lemmas and per-combinator closes
  (`Core.forloop` 39 + `forloop_store` 30, `slotStore_*`) → the fold
  lemma + `commit`. New store shapes cost zero.
- The "compiler order vs. kernel order" mismatch disappears (the log is
  unordered).
- The `Protect` stores of MOD/IDIV/EQ/FORPREP: in the domain premise,
  zero per arm.

### What it costs

- **Setup:** `WriteLog` (a `List (Addr × Byte)` folded into a map), the
  fold lemma `mem_after_stores = mem ⊕ log`, and `commit`. Estimate
  150–220 lines. The fold lemma must handle `sd`/`sw`/`sb` decomposition
  into bytes (little-endian), which the existing `SlotStore` already does
  for one slot.
- **Harder:** a store that overlaps an earlier *load* in the same arm
  (read-after-write within the arm) is not order-free; the log only
  describes the *final* memory. In F1 arms this happens only in FORLOOP (it
  reads R[A..A+2] before storing) and in CALL (the callee reads what the
  arm wrote to `L->top`). Both are fine because reads precede writes in the
  pruned trees, but the rule must state it: the arm's reads are against
  `mem c`, its writes form the log. An arm that reads a slot it already
  wrote needs the ordered form.
- Callee frames below `sp`: the log's domain includes an unbounded region;
  the rule must bound it by `RuntimeData.spEntry` minus the stack limit.

### Theories

- **Known, distant (concurrency theory):** Mazurkiewicz traces:
  equivalence of sequences modulo commutation of independent actions;
  disjoint stores are independent letters. [from memory: Mazurkiewicz,
  "Concurrent program schemes and their interpretations", DAIMI PB-78,
  1977]
- **Known, distant (distributed systems):** last-writer-wins registers in
  CRDTs (Shapiro, Preguiça, Baquero, Zawirski, "Conflict-free replicated
  data types", SSS 2011): the log is an LWW map whose merge is order-free
  on disjoint keys. [from memory]
- **Known (databases):** write-sets and the "blind write" commit check of
  optimistic concurrency control (Kung & Robinson, TODS 1981): validate
  the write-set against the declared footprint at commit, not per write.
  [from memory]
- **Novel:** using the kernel's kill ports as the "arbitrary value" part of
  the write-set, so that `HStep` is literally the commit rule's semantics.

### Pilot

Smallest thing: `WriteLog`, the fold lemma for `sb`/`sd`, `commit`.

- **MUL:** log = `{payload(A) ↦ a0 bytes, tag(A) ↦ 3}` (payload first).
  `commit` with `vals = [mul x y]`, domain = `Slots {A} ∪ Below(sp)` (the
  `__muldi3` frame: it is a leaf, so possibly empty).
- **MOD:** log = `{savedpc ↦ pc+1, L->top ↦ ci->top, payload(A), tag(A)}`;
  on the fall-through edge only the first two. Same rule, no new close.
- **EQ:** log = `{savedpc, L->top} ∪ Below(sp)` (luaV_equalobj's frame), no
  def ports. Same rule.
- **Refactor `sim_ADD`:** tag-first store order; the log is the same as for
  MUL's payload-first order. Delete the ADD close.

### Seed

The doubled runs `BB`, `tt`, `ww`, `GG`, `OO`: two writes of the same
thing next to each other, where it does not matter which came first. The
`OU` repeat (`TOOUu`, `OcjOU`) is "the same pair at two places, in either
context".

## 4. Call shapes as three proved rules, with relocation-invariant helper proofs (`CallShape`)

### Idea

Turn L-C3′'s three callee shapes into **three proved call rules** in the
arm logic, each taking a *shape witness* rather than a per-helper contract:

```
call_pure    : PureWitness f F  → (jal f at state c with a0..a7 = args) →
               ∃ c', c ⟶⁺ c' ∧ pc c' = ra ∧ a0 c' = F (dec args)
                   ∧ mem c' =_{≥ sp \ outs} mem c ∧ calleeSaved c' = calleeSaved c
call_runtime : RuntimeWitness f Φ E → … ∧ mem c' =_{¬Φ} mem c ∧ E (view c) (view c')
call_noret   : NoretWitness f → ¬ ∃ c', c ⟶* c' ∧ AtHead c'   -- and exit ≠ 0
```

`F` is **taken from δ**, not written per helper. The map from helper
symbol to its `F` is a table with one row per helper: `__muldi3 ↦ BinOp.int
.mul`, `__moddi3 ↦ C's %` (truncated), `__divdi3 ↦ C's /`, `luaV_equalobj ↦
δ .eq` (modulo interning), `l_strcmp ↦ lexLt`-sign. The witness is a proof
that the helper's machine code computes `F`, and here is the move that
avoids "one hand-written contract per helper": **the witnesses already
exist**, at other addresses (`Muldi3Spec`, `udivdi3_spec`, `MemcpySpec` at
WHILE addresses, per the census). Prove **once** that the Sail step
relation is *translation-invariant on position-independent code*: if a code
block uses only pc-relative control flow (`jal`, `j`, `beq`, `auipc` pairs
resolved within the block) and no absolute code address, then any run of
the block at address `a` is mapped to a run at `a + d` by shifting `pc`. A
helper proof at the WHILE address then transports to the Lua ELF's address
by one instance of this theorem plus a byte-equality check of the code
(which is `decide` over the text bytes).

For the soft-int helpers this is the whole contract problem for MUL, MULK,
MOD, MODK, IDIV, IDIVK (4 helpers, 316 checked activations). `__moddi3`/
`__divdi3` have no spec yet ("sites only"): they are thin wrappers around
`__udivmoddi4`-style code with sign fix-ups; write their spec *as* `F`
applied through the `udivdi3` witness (one composition lemma each: they
call the unsigned one). That is still per-helper, but 2 helpers × ~20
lines, reused by 4 opcodes each.

`call_noret` is the error chain: MOD/IDIV's `n = 0` path and the stuck
kernel states. Its witness is **not** a contract per function of the 81
error functions; it is a *global* property: `luaD_throw` → `longjmp` to
`luaD_rawrunprotected`'s frame, then the harness's `main` exits nonzero.
One witness for the *landing pad* (`errorJmp->status ≠ 0` → `main`'s exit
code ≠ 0), plus the fact that every `luaG_*error` reaches `luaD_throw`
without returning (a reachability fact on the static call graph, checked,
not searched: the functions are `noreturn` in the C source and GCC emits no
return path; the checker confirms "no `ret` reachable from entry without
passing `luaD_throw`"). The 81 functions' *effects* do not matter because
nothing after the longjmp reads them except the exit path.

### Core rules

- **L-C3′ pure → `call_pure`** with a translated witness.
- **L-C3′ noreturn → `call_noret`**: one landing-pad lemma + a
  no-return-path property of the error entry points.
- **L-C3′ runtime → `call_runtime`**: the rule is proved once; the witness
  for `CALL print` remains the one expensive thing (see costs).
- **L-C6′ "callee frame below sp" → the `=_{≥ sp \ outs}` clause**,
  which is idea 3's `Below(sp)` domain.

### What it makes free

- (b) for the 10 of 11 normal-path helpers that are pure (census): the
  contract is a δ-row plus a translated or composed witness.
- The noreturn side of MOD/IDIV/MODK/IDIVK/FORPREP (the `n%0`, `n//0`,
  `'for' step is zero` errors) and the `stuck_sim` obligation for them: one
  landing-pad lemma.
- `luaV_tointeger`'s out-pointer (`sp+40`): `outs` in `call_pure`.

### What it costs

- **Setup:** the translation-invariance theorem for Sail RV64 on
  pc-relative code. This is real work: Sail's `execute` for `jal`/`branch`
  computes `PC + imm`, so it is structurally true, but `auipc` + `ld` pairs
  that load *absolute data* addresses (the `gp`-relative `.rodata` reads)
  are not code-relative; the theorem must require data addresses to be
  equal (not shifted). Estimate 200–400 lines; risky. If the WHILE and Lua
  builds use the *same* libgcc object bytes, the check is `decide` on
  bytes; if GCC versions differ, the transport fails and each helper needs
  its own proof.
- `CALL print`'s runtime witness (81 functions, ~9k instructions): this
  idea does not make it cheap. It makes it *one* witness (a footprint Φ and
  an effect E = "append `printLine H args`") rather than 81 contracts, but
  that witness still has to be proved. I do not have a cheap proof of it;
  see idea 5 for how the arm side uses it.
- EQ's `luaV_equalobj` is pure only modulo interning (see top). Its `F` is
  `δ .eq` on decoded values *given* the heap invariant.

### Theories

- **Known, distant (physics / group theory):** Noether-style use of a
  symmetry: a translation-invariant dynamics carries solutions to
  solutions. Here the symmetry group is `ℤ` acting on pc for PIC blocks.
  [textbook]
- **Known (linkers):** position-independent code and relocation
  (Levine, *Linkers and Loaders*, 1999); the proof-carrying version is
  "certified linking": Kumar, Myreen, et al. CakeML's relocatable code;
  Wang, Wilke, Shao, "An abstract stack based approach to verified
  compositional compilation to machine code", POPL 2019 (CompCertX /
  CompCertELF). [from memory, check the exact titles]
- **Known (effect systems):** Gifford & Lucassen, "Integrating functional
  and imperative programming", LFP 1986: effect classes pure / read /
  write / allocate, i.e. the call-shape lattice. [from memory]
- **Novel:** reusing proofs made at another binary's addresses by a proved
  translation symmetry of the ISA semantics, checked by byte equality.

### Pilot

Smallest thing: `call_pure` for leaves (no callee frame, no out-pointers),
and the transport of `Muldi3Spec` to `0x8002f6c8`.

- **MUL:** `call_pure __muldi3 (mul)`; the witness is transported
  `Muldi3Spec`. Check first: are `__muldi3`'s bytes at `0x8002f6c8` equal to
  the WHILE build's (`mv a2,a0; li a0,0; andi a3,a1,1; …`, a shift-add
  loop)? If yes, MUL is the cheapest held-out arm.
- **MOD:** `call_pure __moddi3 (C %)` + the fix-up to `imod` (a value
  lemma: `r ≠ 0 ∧ (r xor n) < 0 → r + n = Int.fmod`), + `call_noret` on
  `n = 0`. `__moddi3` needs a new composed witness.
- **EQ:** `call_pure luaV_equalobj (δ .eq)` restricted to the value classes
  F1 puts in registers; for non-string classes `luaV_equalobj` is a tag
  switch and payload compare, provable directly (~40 instructions). Strings
  need the interning invariant.
- **Refactor `sim_ADD`:** no call; ADD is unchanged by this idea (the
  float path's `__adddf3` is pruned by idea 2).

### Seed

The `Dl` / `DL` / `lD` repeats at offsets 9, 43, 79: the same content at
different addresses (relocation). The digit clusters `3661` and `496`
(two numbers that differ by a shift) and the `20…0` padding (`HQS20y0F`,
an offset with zeros).

## 5. Kernel-directed product execution with call nodes (`KProd`, SymExec v2)

### Idea

Build a verified executor that runs the machine arm **in lockstep with the
kernel term**, not on its own. The executor's state is a pair:
(symbolic machine state, kernel position), where the kernel position is one
of: *reading ports*, *case split on port values* (the body's `match`),
*chose edge e*, *committed*. The machine side is executed symbolically as
SymExec did; the kernel side is a *program* the executor consults:

- at a machine branch, the executor asks idea 2's `factor_guard` which
  kernel case predicate the branch decides, and **splits the kernel side
  the same way** (the product), so every machine path is labelled with a
  kernel case, and paths whose label is infeasible for the kernel are
  pruned by the label, not by a separate lemma;
- at a `jal f` whose target is in the call-shape table (idea 4), the
  executor takes a **call node**: it applies `call_pure`/`call_runtime`/
  `call_noret` as a rule of the executor (havoc below sp, `a0 := F(args)`,
  callee-saved preserved; or havoc Φ with the effect E; or close the path as
  noreturn);
- at the return to the head, it applies idea 3's `commit` with the
  labelled kernel edge.

This fixes SymExec's three losses:

1. **Cost 2–4×:** SymExec's hand lines went into per-arm glue relating
   its output to `VmRel` (path conditions to kernel cases, final memory to
   `ValRepr`). In the product, both relations are *built into* the
   executor's step: path conditions are kernel labels (idea 2), final memory
   is a log with a commit (idea 3). The per-arm hand is `KProd.run (arm :=
   opcode) (shapes := table)`, and the arm theorem is an instance of one
   soundness theorem. Target: ≤ 10 hand lines per arm, 0 generated.
2. **No call nodes:** added as above, with shape witnesses as the only
   per-helper input; the executor's soundness is proved once for the three
   node kinds.
3. **Weaker theorem (`SymOk`, `VmRelZ`):** the round-2 fixes already
   carry `RegsOk` and total reads in `VmRel`, so `VmRelZ = VmRel`
   (ROUND-2 "on our side"). The product's soundness theorem is stated
   directly as `sim_X`'s type: `VmRel → Step → ∃ c' n, 0 < n ∧ StepsN n c
   c' ∧ VmRel c' s'`. `n > 0` is by construction (at least the dispatch
   `jr`).

The product also changes what "a new tree" costs: a new tree is *nothing*
unless it contains a new test shape (a `Factors` instance, idea 2), a new
helper (a table row + witness, idea 4), or a new store width (the log
fold, idea 3). The 19 remaining trees reduce to: shift-amount tests
(SHL/SHR/SHLI/SHRI: `bltu`/`bge` against 64, one instance), the `n+1 ≤u 1`
test (MOD/IDIV, one instance), `l_strcmp`'s sign (LT/LE), LOADNIL's loop
(see costs), and the runtime calls.

### Core rules

- **L-C4 → `KProd.sound`**: every complete product run from a `VmRel`
  state ends at the head in `VmRel` with `kstep s`. Proved once.
- **L-C2′ → the product's labelling**: two arms with the same pruned tree
  produce the same labelled product modulo the ALU op; since the executor
  is run, not written, sharing is free and no row is written by hand
  beyond the opcode's `BinOp`.
- **L-C3′ → call nodes** (idea 4's three rules as executor steps).
- **L-C6′ → the commit step** (idea 3).

### What it makes free

- (a1) new trees, (a4) guards, (a5) inversions, (c) closes: all executor
  runs.
- (d4) generated volume: 0 generated lines (like SymExec).
- (a2)/(a3) layouts and rows: layout is irrelevant to an executor; rows
  are the δ-table already in `opKernel`.

### What it costs

- **Setup:** the largest of the five. The SymExec copy (2,442 lines) plus
  the product layer (kernel position, labelled splits), call nodes, and the
  commit. Estimate 600–900 hand lines on top of SymExec. The payoff is
  only real if the per-arm hand line count really falls to ~10; the
  held-out pilot decides it.
- **Harder:** loops *inside* an arm. LOADNIL (`setNils`, a C loop over
  `n` slots) and `__muldi3` itself (a shift-add loop) are not finite
  trees. The executor needs a loop node with an invariant; for LOADNIL the
  invariant is the kernel's `List.range'`, i.e. the log after `k`
  iterations is `{tag(A+i) ↦ 0 | i < k}`. One more node kind, proved once;
  the invariant is read from the kernel (the def port list), not written.
- Executor performance (CPU, memory) under `decide`-heavy guards: SymExec
  was 5–7 s per arm; the product adds kernel evaluation, which is cheap
  (`opKernel` is small).
- The `CALL print` runtime witness is still needed (idea 4's cost). The
  product makes CALL's *arm side* free; it does not prove `luaB_print`.

### Theories

- **Known:** product programs for relational verification: Barthe,
  Crespo, Kunz, "Relational verification using product programs", FM
  2011; Zaks & Pnueli, "CoVaC: compiler validation by program analysis of
  the cross-product", FM 2008. [from memory]
- **Known, distant (bioinformatics):** pairwise sequence alignment
  (Needleman & Wunsch, J. Mol. Biol. 48, 1970): two sequences aligned by
  matching "columns"; here the machine path and the kernel's evaluation
  are aligned at guard/branch columns and at the commit column, with gaps
  (machine steps that the kernel does not see: address arithmetic, the
  `Protect` stores). [from memory]
- **Known (translation validation):** Pnueli, Siegel, Singerman,
  "Translation validation", TACAS 1998; Necula, "Translation validation
  for an optimizing compiler", PLDI 2000. The product executor is a
  translation validator from the kernel term to the arm. [from memory]
- **Novel:** a kernel-labelled product executor whose call nodes are
  indexed by effect shape, so the same soundness theorem covers inline and
  helper-calling arms.

### Pilot

Smallest thing to build: the product layer over the existing SymExec copy,
with *only* the pure call node and the commit step; no loop node, no
runtime node.

- **MUL:** product run: split on `tagB == 3` (kernel label: `B` int / not),
  `tagC == 3`, call node `__muldi3`, commit. The run must reproduce the
  pc+2 edge with `R[A]` and the pc+1 edge (via the default tail
  `0x8001c1e4`) with nothing.
- **MOD:** product run with the `protect` stores in the log on both edges;
  the `n ∈ {0,−1}` split; the noreturn leaf needs `call_noret` (if not
  ready, the pilot stops at "the `n = 0` path is closed by an axiom of the
  shape" and reports the gap).
- **EQ:** call node `luaV_equalobj`, then the trap reload (complement
  read), then the label on `k = a0`, then `donextjump` (reads the next
  instruction word: the product reads the kernel's `nextJump p pc`, which
  is exactly the same fetch).
- **Refactor `sim_ADD`:** replace the generated file with the one-line
  product invocation; compare lines against the incumbent's 61.

Bake-off metric: hand lines per held-out arm (target ≤ 15), and whether
MOD and EQ are expressible at all (the round-2 disqualifier).

### Seed

`Mimid` / `EimidI` (two halves mirroring around `d`: the machine and the
kernel as the two sides of one alignment), `M9M` in `qM9Mg` (the same
symbol on both sides of a gap: aligned columns with a gap between), and
the palindromes `8i8`, `0y0` as "each side has a matching column".
